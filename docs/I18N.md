# Internationalization (i18n) & Localization

SVBooking ships a bilingual UI: **English (`en`, authoritative)** and **Hebrew
(`he`, RTL)**. The system is intentionally **client-side** — there is no
server-side locale negotiation or per-locale routing. This document is the
single source of truth for how it works, how to extend it, and the one known
gap (RTL physical-property mirroring).

## Architecture

| Piece | File | Responsibility |
|-------|------|----------------|
| Dictionary | `lib/i18n.js` (`CORE_TRANSLATIONS`) | All UI strings, keyed, one block per locale (`en`, `he`) |
| Locale config | `lib/i18n.js` (`SUPPORTED_LOCALES`, `LOCALE_QA_MATRIX`) | `en`/`he` are full; `ar`/`fr`/`es` are fallback-only QA placeholders (`contentTranslation: 'partial'`) |
| Runtime provider | `components/LocaleProvider.tsx` | React context; reads the persisted locale from `localStorage` on mount, exposes `useLocale()`, and sets `document.documentElement.{lang,dir}` |
| Switcher | `components/LocaleSwitcher.tsx` | EN/HE toggle |
| Readiness/QA | `lib/i18n.js` (`getI18nReadiness`, `buildLocaleQaReport`) | Surfaced via `/api/i18n` and health-readiness |

Locale is **persisted in `localStorage` only** (no cookie). Consequently the
server always renders the default locale (`en`) — which is also the canonical
SEO language (see `hreflang` alternates) — and the client re-renders into Hebrew
after hydration for `he` users. This is why every localized screen is (or
delegates to) a **client component**.

## Consuming translations

```tsx
'use client';
import { useLocale } from '@/components/LocaleProvider';

// Local helper, used wherever a string has {placeholders}:
function interpolate(t: string, v: Record<string, string | number>) {
  return t.replace(/\{(\w+)\}/g, (_, k) => String(v[k] ?? `{${k}}`));
}

const { t, locale, dir } = useLocale();
t('comparePrices');                                   // → "Compare prices" / "השוואת מחירים"
interpolate(t('hdSavings'), { pct, currency, amount }); // interpolated
```

`t(key)` returns `dict[key] ?? key` — an unknown key renders as itself, never
throws. `useLocale()` outside a provider falls back to English (safe for tests).

## Adding a new key

1. Add the key to **both** the `en` and `he` blocks in `lib/i18n.js`.
2. Keep the **same `{placeholder}` tokens** in both locales.
3. Prefer reusing an existing key when the text matches exactly (e.g.
   `compareCheckIn`, `chPerNight`, `compareCheapest`, `navFavorites`).
4. Group by feature with a `// Comment` header (e.g. `// Hotel detail page`).

The test suite enforces correctness — see **Testing** below.

## Patterns

- **Server components** (SEO/static pages like `app/city/[name]/page.tsx`):
  keep the page a server component and extract only the localizable chrome into
  a small client component. See `components/CityLabels.tsx`.
- **Dates / months / weekdays**: never hardcode English name arrays. Use
  `Intl.DateTimeFormat` with a BCP-47 tag derived from the locale
  (`locale === 'he' ? 'he-IL' : 'en-US'`). See `PriceCalendar`,
  `BestTimeToBook`, `DestinationIntel`. Hebrew single-letter weekday headers are
  the one exception (a fixed `['א','ב','ג','ד','ה','ו','ש']` array).
- **Pluralization**: pass a locale-specific word into the template rather than
  appending `'s'` — e.g. `bttbWeekdayPlural` is `'{day}s'` (en) / `'ימי {day}'`
  (he); `citySubtitle` takes a `{hotelWord}` chosen by count.
- **Legal documents** (`privacy`, `terms`): English is **authoritative** and
  server-rendered for SEO; Hebrew is a **convenience translation** prefaced with
  a disclaimer that the English version governs. Content lives in
  `lib/legal-content.ts` (maintained as whole documents, *not* scattered
  dictionary keys) and renders through `components/LegalDocument.tsx`, which
  supports lightweight `**bold**` and `` `code` `` inline markers.
- **Internal/admin tooling is intentionally English-only.** `components/AgentDashboard.tsx`
  (the `/agents` ops console: provider latency, circuit breakers, candidate
  queue) is not localized — operational/observability tooling is conventionally
  English and the terminology is clearer that way.

## Testing & gates

| Gate | What it guarantees |
|------|--------------------|
| `tests/i18n-dictionary.test.ts` | `en`/`he` have identical key sets; no empty values; fallback behavior |
| `tests/i18n-placeholders.test.ts` | **Every** key has matching `{placeholder}` sets across locales; no unbalanced/empty braces |
| `tests/i18n-readiness.test.ts` | Locale config / readiness payload shape |
| `tests/components/HomeI18n.test.tsx`, `LegalDocument.test.tsx` | Component-level EN→HE switching renders correctly |
| `npm run audit:i18n` | i18n infrastructure markers present in `lib/i18n.js`, `app/api/i18n/route.js`, `app/layout.tsx`, `LocaleProvider`, health-readiness |

Run them all: `npx vitest run tests/i18n-*.test.ts tests/components/*I18n*.test.tsx && npm run audit:i18n`.

## Coverage

End-user surface is fully localized (`en`/`he`): home, search, deals, explore,
about, compare, compare-hotels, contact, favorites, hotel detail, city,
privacy/terms, dashboard, trips, profile, navbar, footer, and the shared
components (RatingBadge, SearchFilters, DestinationIntel, PriceCalendar,
BestTimeToBook). `AgentDashboard` is intentionally English (see above).

## Known gap — RTL physical-property mirroring

`LocaleProvider` sets `dir="rtl"` for Hebrew, so **text direction and flexbox
order mirror automatically**. However, most components style spacing and
position with **physical** Tailwind utilities (`ml-*`, `pl-*`, `left-*`,
`right-*`, `text-left`) which do **not** flip under `dir=rtl`. The result: text
reads correctly, but some icon gaps, paddings, and absolutely-positioned
elements remain on their LTR side in Hebrew.

**Remediation (follow-up):** migrate physical utilities to Tailwind **logical**
equivalents — `ms-*`/`me-*` (margin), `ps-*`/`pe-*` (padding),
`start-*`/`end-*` (inset), `text-start`/`text-end` — and verify each screen
visually in a browser at `dir=rtl`. This is a cross-cutting change best done as
a dedicated, browser-verified pass rather than blindly, since a partial
conversion can look more inconsistent than uniform physical layout. Today only
`tailwind`-logical usage exists in a single file; the rest is physical.
